Aufbau

Sechs Automaten ineinander

Es gibt nicht die Zustandsmaschine des Laufs. Es gibt sechs, geschachtelt, und jede speichert ihren Zustand an einem anderen Ort. Das ist die wichtigste Eigenschaft des ganzen Entwurfs und zugleich der Grund, warum er sich schwer überblicken lässt: kein einzelner Prozess hält den Zustand, und keiner muss es. Wer stirbt, hinterlässt ihn in Dateien.

Ebene 2 liest von Ebene 3 allein die Marke; Ebene 3 erfährt von Ebene 5 allein, was der Runner am Ende in den Plan schreibt, und die Schleife prüft es gegen git nach. Wer eine Ebene nachbauen will, muss ihre Schnittstelle zu den Nachbarn exakt einhalten — der Rest ist ihr Inneres.

Akteure, wie sie in den Tabellen stehen: Orchestrator ist die Session, die plant, startet und abschließt. A fährt Zug 0 im tmux-Fenster, B die Züge 1–5 als claude -p, N den nachgezogenen Review. Schleife ist remediate.sh, Nutzer der Mensch.

Ebene 2

Die Schleife

remediate.sh läuft zweimal an. Der äußere Aufruf prüft die Vorbedingungen, legt die tmux-Session an, kopiert das Skript nach $WORK/remediate.snapshot.sh und endet sofort mit 0. Der innere — die Kopie, mit REMEDIATE_INSIDE=1 — prüft noch einmal, nimmt die Sperre, setzt den einzigen EXIT-Trap und schreibt Lauf-Status: läuft seit …. Erst dann beginnt der Zyklus.

Vorbedingungen (Exit 40)

Werkzeuge claude jq git sed grep awk vorhanden; ein Git-Arbeitsbaum; Plan und Rückgabeschema existieren, das Schema ist gültiges JSON; der Plan-Kopf nennt einen Branch, und genau der ist ausgecheckt; das Arbeitsverzeichnis lässt sich anlegen; der Arbeitsbaum ist sauber, abgesehen vom ungetrackten Plan und docs/remediation/; der Plan enthält mindestens ein Paket. Nur außen: tmux vorhanden, keine gleichnamige Session. Nur innen: die Sperre ist frei, ein Terminal ist da.

Ein Durchlauf

iter ← iter + 1
wenn iter > MAX_ITER (200)                   → Exit 20
wenn iter = 1 ∧ ∃ [~]                       → Exit 11   # Rest eines gestorbenen Laufs
wenn ∃ [r]  → Rolle N auf dem obersten [r]         # Vorrang: kein Weiterbauen auf ungeprüftem Commit
sonst wenn ∃ [~]  → Rolle B auf dem obersten [~]
sonst wenn ∃ [ ]  → Rolle A auf dem obersten [ ]
sonst  → Lauf-Status »Schleife durch · Abschluss offen«, Meldung, Exit 0
wenn --once ∧ PACKAGES_DONE ≥ 1             → Lauf-Status »nach --once angehalten«, Exit 0

»Oberstes« heißt: erste Überschrift dieser Marke im Dokument. Die Reihenfolge der Pakete ist also ihre Stellung in der Datei, nicht ihre Nummer. [!] und [x] wählt die Schleife nie aus. Ein blockiertes Paket, das niemand wieder öffnet, bleibt deshalb bei einem Neustart liegen, und der Lauf fährt die übrigen zu Ende — gewollt, und der Abschluss verweigert dann den zweiten Commit.

PACKAGES_DONE zählt ein [x] aus Zug 0, ein committed oder dropped von B und ein committed von N. Ein Commit ohne Review-Beleg zählt nicht: das Paket steht auf [r] und ist noch nicht fertig.

Ebene 3

Das Paket

Das Herz des Ganzen. Fünf Marken, ein Endzustand, eine Senke. Der Automat hat eine Eigenheit, die ihn von einem Lehrbuch-Automaten trennt: den Übergang schreibt fast immer der Akteur selbst, und die Schleife prüft ihn danach. Nur [r] setzt die Schleife eigenhändig.

Wie Pakete entstehen

Ein Paket wird in L5 als [ ] geboren, danach auf drei Wegen: A teilt sein eigenes Paket (3 wird 3a und 3b); A schneidet für eine echte Folge ein neues Paket mit Folge von: und sortiert es nach den Phasen ein; der Drain in D0 hängt für → Scope ein Paket ans Ende. Nummern werden nie neu vergeben. Ein Paket verschwindet nie: auch »entfallen« ist ein [x] mit Begründung.

Die dritte Generation einer Kette, ablesbar an Folge von:, darf A nicht mehr selbst schneiden — dann ist der Weg des ersten Pakets das Problem, und die Kette geht an den Nutzer.

Ebene 4

Das Fenster von Zug 0

Die Schleife beaufsichtigt A, ohne ihn zu verstehen. Sie kennt vier Signale: die Datei paket-N.zug0.done, die Existenz des Fensters, die Prüfsumme von Plan und Paketdatei, die Prüfsumme des Panes. Dazu die Frage, ob ein Mensch erreichbar ist. Alle fünf Sekunden (ZUG0_POLL) ein Blick, in dieser Reihenfolge; der erste Treffer gewinnt.

BedingungÜbergangFrist
Feierabendzeichen existiertGnadenfrist, dann /exit, dann notfalls kill-window → AuswertungGRACE 20 s · CLOSE 20 s
Fenster ist weg (Nutzer hat es geschlossen, Prozess beendet)→ Auswertung—
Pane zeigt den Vertrauensdialog der CLIUhr läuft; abgelaufen → Fenster zu, Exit 40TRUST_GRACE 60 s
Marke fertig laut Plan ([~] mit Paketdatei, oder [x], [!]) und Stilleerster Treffer → Stupser ins Fenster; nach weiterer Stille → Fenster zu → AuswertungSETTLE 120 s, zweimal
niemand erreichbarUhr zählt hoch; abgelaufen → Fenster zu, Exit 10TIMEOUT 1800 s

Stille hat zwei Uhren. Die eine misst, wie lange Plan und Paketdatei unverändert sind, die andere, wie lange der Pane unverändert ist. Maß ist die kürzere — ein Planer, der noch schreibt oder noch redet, wird nicht angestupst. Ausnahme: stehen die Dateien schon dreimal SETTLE still, zählt der Pane nicht mehr mit, sonst hielte eine zuckende Statuszeile die Erkennung ewig auf. Jede Änderung an den Dateien setzt beide Uhren zurück und gibt einen neuen Stupser frei.

Erreichbar ist der Nutzer, wenn ein tmux-Client an der Session hängt oder in Mitschrift oder Scrollback des Fensters remote-control is active steht; ZUG0_ASSUME_USER=1 behauptet es von außen. Solange er erreichbar ist, steht die Timeout-Uhr auf null. Nie erreichbar gewesen zu sein wird festgehalten — für die Probe danach.

Auswertung nach dem Fenster

wenn nie erreichbar ∧ ¬ASSUME_USER ∧ »Entscheidungen« ≠ Stand bei Fensterstart → Exit 20
sonst Marke lesen: [~] → weiter · [x] → PACKAGES_DONE+1, weiter · [!] → Exit 10 · alles andere → Exit 10

Die Marke ist die Rückgabe von A. Ein Ergebnis-JSON gibt es nicht; A ist eine TUI, und was er am Ende ins Terminal schreibt, liest niemand. Das Feierabendzeichen sagt nur, wann er fertig ist, nie was herauskam.

Ebene 5

Die Züge 1–5

Gefahren von B, im Inneren eines einzigen claude -p. Die Schleife sieht davon nichts außer der Rückgabe und den Dateien; alles hier ist Prosa in runner.md, die ein Modell befolgt. Deshalb ist diese Ebene die einzige, deren Übergänge niemand erzwingt — nur ihre Spuren werden nachgezählt.

Der Wächter vor dem Commit

commit erlaubt ⇔ Verify grün ∧ t(Verify) > t(letzte Codeänderung) ∧ Review ohne offene kritische oder wichtige Befunde ∧ jedes Finding erfüllt

Lag zwischen dem letzten grünen Lauf und dem Commit keine Änderung, wird nicht erneut verifiziert; verify_log zeigt dann auf den Lauf aus Zug 2. Pre-Commit-Hooks laufen mit, ein abbrechender Hook ist ein Befund für die Kette. Der Commit trägt den Trailer Remediation-Run: <Plan-Datum>.

Die Bremse der Fehlerkette

Sei Ok die Menge der offenen Befunde nach Runde k und Ek die Menge der bis dahin erledigten. Runde k hat Fortschritt gemacht, wenn sie einen vorher offenen Befund erledigt und keinen erledigten zurückholt:

fortschritt(k) ⇔ (Ok−1 ∖ Ok) ≠ ∅ ∧ (Ek−1 ∩ Ok) = ∅
tausch(k) ⇔ fortschritt(k) ∧ |Ok| ≥ |Ok−1|
letzte Runde ⇔ ¬fortschritt(k) ∨ (tausch(k−1) ∧ tausch(k)) ∨ k = MAX_ROUNDS

Ein Befund, den erst die Runde selbst verursacht hat, ist ausdrücklich kein Rückschritt: er landet in Ok, ohne Fortschritt aufzuheben. Erst wenn zwei Runden hintereinander nur tauschen, erzeugt jeder Fix seinen Nachfolger — dann ist Schluss.

Blockieren und wieder aufnehmen

Endet die Kette ohne Erfolg, schreibt B in dieser Reihenfolge: Marke [!] mit den offenen Befunden in einer Zeile; git stash push -u -m "paket-N-abgebrochen" ohne Plan und Paketdateien; den Stash-Namen als letzte Verlaufszeile; Stand: auf das nächste Paket; Rückgabe blocked mit der Angabe, ob die offenen Befunde Folgen des eigenen Diffs sind und ob Verify im gesicherten Stand grün war. Der Baum ist danach sauber.

Öffnet jemand das Paket wieder ([!] → [ ]), liest A den Stash, ohne ihn anzuwenden, und plant gegen Code und Stash. B holt ihn vor Zug 1 mit git stash apply zurück — gesucht wird immer über den Namen, weil stash@{n} wandert —, die Kette beginnt neu bei Runde 1, und nach dem Commit fällt der Stash mit drop. Ein Konflikt beim Zurückholen ist selbst ein blocked.

Ausgänge

Exit-Codes und Rückweg

Jeder Ausgang der inneren Schleife läuft durch denselben Trap: Journalzeile ende exit=N, Sperre weg, und bei N ≠ 0 Tokentabelle in den Plan, Lauf-Status: angehalten mit Exit N bei Paket M und eine Desktop-Nachricht. Nur kill -9 und ein Stromausfall entkommen ihm; dann verschwindet die Sperre nicht, oder sie verschwindet ohne ende-Zeile, und genau daran erkennt der Wachposten den Tod.

Der Wachposten

Die Schleife hält den Orchestrator über das Journal wach, ein Monitor filtert die Zeilen. Er ist ein Automat mit zwei Zuständen und einer Eingabe: »warte auf Sperre« (höchstens 60 s, sonst: Schleife nie angelaufen) und »wache«, bis ende exit= kommt oder die Sperre ohne diese Zeile verschwindet.

JournalzeileOrchestrator
status=committedPush: Paket, Kurzhash, Stand
status=dropped, marke=[x]Push, knapp
status=review-offennichts — die nächste Zeile zu dem Paket kommt von N
status=questionPush mit der Frage
status=blocked, marke=[!]fünf Bedingungen prüfen: entscheiden und pushen, oder fragen
ende exit=0Push, sofort L7
ende exit=NPush mit N, Exit-Tabelle

Zusicherungen

Invarianten

Was in jedem erreichbaren Zustand gilt. Die ersten fünf erzwingt Code, die übrigen nur Prosa — die Liste sagt bei jeder, welches von beiden.

Eine Schleife je Arbeitsbaum. Code
mkdir .remediate.lock ist atomar; die Sperre existiert genau, solange eine innere Schleife läuft.
Ein Runner zur Zeit. Code
Die Schleife ist sequentiell und wartet jeden Runner ab; ein [~] beim Start hält sie an.
Kein Weiterbauen auf ungeprüftem Commit. Code
[r] hat Vorrang vor jeder anderen Marke.
Keine Entscheidung ohne Entscheider. Code in Zug 0
»Entscheidungen« wächst in Zug 0 nur, wenn der Nutzer erreichbar war. Dass der Orchestrator seine eigenen Einträge kennzeichnet, ist Prosa.
Der Plan bleibt draußen. Code an der Vorbedingung
Plan und docs/remediation/ sind während des Laufs ungetrackt. Die Vorbedingung blendet genau diese beiden aus, und nur, solange sie ungetrackt sind; dass git add, diff und stash der Runner sie ebenfalls ausnehmen, ist Prosa.
Wer committet, hat verifiziert. Prosa, nachgezählt
B fährt Verify selbst; die Schleife prüft exit=0 im Log, nicht, ob das Log jünger ist als die letzte Änderung.
Kein Code aus der Hand des Runners. Prosa, nachgezählt
Die Anzahl der Implementierer-Reports belegt Delegation; fehlt sie, wird es vermerkt, nicht verhindert.
Nur ein Implementierer gleichzeitig. Prosa
Nichts prüft es.
Kein Push, kein Tag, kein Publish. Code für B und N
Die Verbotsliste hängt am Prozess von B und N. Die Implementierer und Reviewer, die B startet, bekommen laut runner.md keine eigene mit; für sie, für Zug 0 und für die Session gilt es per Prosa.
Der Lauf endet nicht mit Schulden. Prosa
D0 läuft, bis »Offene Befunde« und alle Folgen: leer sind; der zweite Abschluss-Commit setzt es voraus.

Befund

Was die Formalisierung aufgedeckt hat

Beim ersten Aufschreiben passten die Tabellen an vier Stellen nicht zueinander. Alle vier sind am 2026-09-25 behoben, gegen einen Stub der Schleife über 25 Prüfpunkte gefahren; derselbe Stub gegen das alte Skript fällt an genau diesen Stellen.

Eine Frage hatte keinen Parkplatz

blocked sicherte den Stand im Stash, question ließ ihn im Baum und die Marke auf [~]. Der Neustart nach der Antwort endete dann mit Exit 40 (Baum schmutzig) oder Exit 11 ([~] im ersten Durchlauf). Jetzt parkt question wie blocked: [!], Stand im Stash, sauberer Baum; die Schleife prüft beides und endet sonst mit Exit 20. Wieder aufgenommen wird über denselben Weg wie ein blockiertes Paket — nur entscheidet bei einer Frage immer der Nutzer.

Die Wächter kamen nach dem Übergang

B setzte [x] selbst, und eine danach gescheiterte Probe ließ das [x] stehen; ein Neustart übersprang das Paket. Jetzt setzt die Schleife jedes Paket, an dem eine Probe fällt, selbst auf [!] und schreibt Gegenprobe gescheitert mit dem Grund darunter. Der Runner schreibt seinen Übergang weiterhin selbst, aber er kann keinen behalten, den die Probe nicht bestätigt — dieselbe Umkehr, die für den fehlenden Review mit [r] schon galt.

Drei Zählweisen für eine Runde

Schema, runner.md und check_commit zählten verschieden, und die Probe zählte -versuch--Dateien, bei N auch die Reports von B und bei einem wieder geöffneten Paket die seines ersten Anlaufs. Jetzt gilt überall: Runde 0 ist der Implementierer aus Zug 1, rounds zählt die Runden der Kette danach, und es darf höchstens rounds + 1 Implementierer-Reports geben. Gezählt werden nur Dateien, die jünger sind als der Start des Runners, ohne Versuchsdateien.

Ein blockiertes N hatte keinen Rückweg

Wieder geöffnet wurde jedes [!] auf [ ], und ein committetes Paket fuhr damit noch einmal durch Zug 0 und B. Jetzt sieht die Schleife vor jedem Zug 0 nach, ob unter dem Paket ein Hash steht, den es im Repo gibt. Dann ist es kein offenes, sondern ein wieder geöffnetes Paket: sie setzt es auf [r], vermerkt das, und N holt den Stand aus dem Stash und setzt fort. Wer wieder öffnet, muss den Unterschied nicht kennen.

Was bleibt

  • Der Status planned steht im Schema und wird nie gesendet: A hat kein Schema. Jetzt ausdrücklich so beschrieben, aber weiterhin ein toter Zustand im Vertrag.
  • Der Wächter »Verify jünger als die letzte Änderung« ist Prosa. Die Schleife prüft nur exit=0; ein altes grünes Log unter einem neueren Diff bestünde die Probe.
  • Ein Neustart ohne Entscheidung fährt an einem [!] vorbei und endet mit »Schleife durch · Abschluss offen«. Gewollt — aber Lauf-Status: sagt dann nicht, dass ein Paket geparkt blieb.
  • Was ein echtes Modell aus dem geänderten runner.md macht — ob es eine Frage wirklich parkt, ob N einen Stash zurückholt —, prüft kein Stub.

Stand

Die Marke ist die Wahrheit, und das trägt

Der Entwurf hält, weil er seinen Zustand konsequent aus den Prozessen herausgenommen hat: fünf Marken in einer Markdown-Datei, ein Journal, eine Sperre, die Reportdateien. Jede Ebene lässt sich an ihrer Schnittstelle abschneiden und neu bauen, ohne die anderen anzufassen — das ist die Eigenschaft, die eine Portierung auf echten Code überhaupt erst möglich machen würde, ob als TypeScript über dem Agent SDK oder als LangGraph-Knoten.

Die vier Lücken hatten eine gemeinsame Wurzel: der Akteur schrieb seinen eigenen Übergang, und die Schleife prüfte hinterher, ob er ihn verdient hatte — ohne ihn zurücknehmen zu können. Seit dem 2026-09-25 kann sie es. Eine Portierung auf echten Code würde den Schritt zu Ende gehen und die Marke erst setzen, nachdem der Wächter bestanden ist.
